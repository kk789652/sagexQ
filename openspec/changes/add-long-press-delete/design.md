## Context

`CapturedMessage` currently has no id (parser builds it without one), so single-message delete isn't addressable. `MessageEntity` already has an autogenerated `id`. Conversation-level delete exists (`deleteByRange(key, All)`), but the user wants a direct long-press path.

## Goals / Non-Goals

**Goals:**
- Expose `id` on `CapturedMessage` (from the entity) so a message is addressable.
- Long-press → confirm → delete, for both a conversation and a single message.

**Non-Goals:**
- Multi-select delete; undo. (Deletes remain permanent + confirmed.)

## Decisions

**1. Add `id: Long = 0` to `CapturedMessage`.**
`MessageEntity.toDomain()` maps the real `id`; `toEntity()` keeps default 0 so Room autogenerates on insert. Parser-built messages use 0 (never persisted directly without going through Room). Detail list keys can now use the real id instead of the index workaround.

**2. New repository/DAO deletes.**
`MessageDao.deleteById(id)`; `MessageRepository.deleteMessage(id)` and `deleteConversation(conversationKey)` (delete all rows for a key). Both on IO.

**3. Long-press via `combinedClickable`.**
Conversation row and message bubble use `Modifier.combinedClickable(onClick = …, onLongClick = …)`. Long-press opens a confirmation (AlertDialog) naming the target; conversation row keeps its normal tap-to-open.

## Risks / Trade-offs

- **Accidental long-press delete** → always behind a confirmation dialog.
- **id default 0 collisions in non-persisted contexts** → only persisted (Room-sourced) messages are deletable; UI only deletes messages it loaded from storage (real ids).
